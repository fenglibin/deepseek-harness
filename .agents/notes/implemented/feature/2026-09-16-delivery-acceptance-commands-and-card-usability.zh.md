# Agent Note: 交付纪律的验收命令与设置卡片可用性

Status: implemented

## 问题

交付纪律的设置卡片（`设置 → 插件 → 插件配置 → 交付纪律`）有两类问题，一类是呈现缺陷，一类是产品缺口。

呈现缺陷四处：卡片底部渲染出一个游离的 `)` 文本节点（`DeliveryCard.tsx` 里 `</PluginCard>` 之后多写了一个括号，它不在任何 JSX 表达式容器内，因此被 React 当作文本子节点渲染）；帮助链接在展开区单独占一行，与它展开的那句描述断开；14 个字段全部单列纵向排列，配置密度远低于可用空间；强/中/弱信号词表用多行文本域编辑，命中规则只写在问号提示里，「每行一条」没有说明匹配是忽略大小写的子串包含、能填什么值、怎么新增，而词表里的 `replac` 在界面上看起来像拼写错误。

产品缺口是「验收前置命令」：它要求用户手写 shell 命令，普通用户不知道该输入什么。用户希望改为从「提示词命令」页已配置的命令中勾选。

## 决策

### 验收依据从 shell 命令改为提示词命令，门禁锚定在「是否留下记录」

「提示词命令」页编辑的是 `prompt-commands` settings 命名空间的 `commands`，每条经 `@deepseek-ai/dsh-command-prompt-config` 注册为 `kind: 'prompt'` 的斜杠命令——它的 payload 是一段提交给模型的用户消息文本，不是 shell 命令，执行后不产生退出码。原门禁（`postHooks`）恰恰依靠 `exitCode === 0 && !timedOut && !aborted` 判定。把验收依据换成提示词后，这个判定依据消失；若只让模型执行提示词并自述完成，门禁会退化成一句口头承诺，正是交付纪律本身要对抗的失败模式。

因此门禁改锚在**可机械检查的事实**上：`delivery` 命名空间的 `verificationCommands` 取提示词命令名（不含前导斜杠），`advance_delivery_task` 推进到 `verified` 时，若勾选了命令而该任务尚未为每条命令留下执行记录，则阻止推进。记录由模型调用 `record_change` 产生，文本以 `acceptance: <命令名> ` 开头，解析取前缀后的第一个 token 作为命令名，其余是模型自己的观察说明，门禁不解释它。[l0 纳入自检与验收命令按序执行](../architecture/2026-09-17-l0-selfcheck-and-ordered-acceptance-commands.zh.md)随后把「逐命令计数」收紧为「按配置顺序逐条要求」，即每次只要求最早那条未记录的命令。

`postHooks` 字段按仓库的预发布立场直接移除，不做兼容回退；旧值被忽略。该决策部分取代了[交付纪律后置命令](../architecture/2026-09-03-delivery-discipline-post-hooks.zh.md)（用户可配置的验收命令不再走 shell 执行路径），但那条记录中「按 change id 定向校验、空 change id 不插入命令」的决策仍然有效并保留。

### `openspec validate` 结构校验不随本次改动移除

L2 任务在 `verified` 阶段仍由 Host 经 `ctx.shell.run` 执行 `openspec validate <changeId> --strict --json` 并按退出码判定。它校验的是本次 OpenSpec 变更的结构合法性，与「用户想额外跑什么验收」是两件事，因此保留为确定性检查，且与提示词验收互不替代。

### 提示词正文经 settings 描述符读取，并写进门禁消息

验收提示词正文从 `prompt-commands` 命名空间读取（经 `ctx.settings.describe()` 找到该命名空间），而不是从命令注册表读——注册表只暴露 UI 元数据，不含提示词文本；而 settings 分节既是设置界面编辑的对象，又是门禁读取的来源，两者不会对同一命令的正文产生分歧。

正文写进**被抛出的门禁消息**，而不是用 `ToolRunContext.deferContext` 注入：`deferContext` 附加的上下文只在工具**成功**结果上被带走（`packages/core/tools/src/index.ts` 的 `dispatchScheduledExecution`），抛错走 catch 分支会丢弃它。阻止推进时模型必定读到的是门禁消息，指令必须放在那里。选中的命令名在 `prompt-commands` 中已不存在时，门禁照常阻止并说明该命令没有对应提示词，而不是静默放宽要求。

### 词表用标签编辑器，并保留刻意词干

强/中/弱信号词表改为标签式编辑器（一个值一个可删除标签，输入框回车或按钮提交），值形状仍是 `string[]`，因此 Host schema 不变。重复条目被拒绝并就地提示，而不是静默去重。

默认词表中的 `replac`/`upgrad` 是**刻意词干**，不是拼写错误：匹配是子串包含，一个词干覆盖整个词族（`replace`/`replaced`/`replacing`/`replacement`）且只计一次。对三个默认词表做两两包含检查确认没有任何互相包含的条目对，因此词干不会重复计数。反过来若把词干换成整词会更差：`replace` 匹配不到 `replacing`，而 `replace` 与 `replacement` 并存时会各自命中一次（前者是后者的子串），那才是真实的重复计数。字段说明因此解释该写法，并提示用户新增条目时避免互相包含。

### 卡片呈现

游离 `)` 直接删除，并加一条覆盖整个渲染容器的断言——游离文本落在卡片元素之外，只看卡片内部发现不了它。帮助链接移到描述行内：卡片标题行整体是展开/收起按钮，帮助链接也是按钮，嵌套按钮是无效 HTML 且破坏键盘可达性，因此两者成为兄弟节点而非父子。两列栅格由交付纪律卡片自己声明（而非卡片基座），其它字段较少的卡片保持各自的纵向布局。多行控件整行占满，窄视口回落单列。

## 备选方案

**保留 shell 命令清单，另外提供提示词勾选（双轨）。** 否决：用户诉求是降低使用门槛，两套配置项反而增加理解成本；且两套语义要长期维护。

**`postHooks` 保留为回退路径。** 否决：预发布立场是地基优先于影响半径，保留兼容路径会让两套语义长期并存。

**让模型执行提示词后在回复里声明完成，门禁只做提醒。** 否决：这正是原门禁要消除的口头承诺；用户明确选择了硬门禁。

**用 `deferContext` 注入验收提示词。** 否决：`deferContext` 只在成功结果上被带走，抛错路径会丢弃它，因此阻止推进时注入等于什么都没说。

**把词干替换为可读整词。** 否决：实测会漏掉 `replacing` 并让 `replace`/`replacement` 重复计数，比词干更差。

**把词干从词表中移除。** 否决：理由同上，词干本身是正确的写法。

**把两列栅格放在卡片基座（`PluginCard`）里。** 否决：那会顺带改掉其它四张卡片的布局，而它们并不需要两列，且该改动不在本次诉求范围内。

## 后果

- **获得** 普通用户无需知道该填什么命令即可配置验收：候选来自「提示词命令」页已维护的清单。信号词表的规则从「只有提示词里写着」变为「字段说明直接讲清匹配规则、取值与新增方式」。
- **获得** 门禁仍不可被模型口述绕过，且判定依据对读者可见：缺少记录就是缺少记录。L2 结构校验保持确定性。
- **代价** 提示词验收的结论仍由模型自己记录，门禁只能保证「留下了记录」，不能保证记录内容为真。这是用提示词替代退出码的固有代价，也是用户明确选择的方案；原先靠退出码的强保证只保留给 L2 结构校验。
- **代价** 既有部署的 `postHooks` 配置失效，需改配 `verificationCommands`；测试与快照同步更新。
- **代价** 验收命令的候选列表依赖 Host 同时挂载设置服务与提示词命令插件；未挂载时该控件没有候选，卡片给出空态引导。
- **后续变更** [l0 纳入自检与验收命令按序执行](../architecture/2026-09-17-l0-selfcheck-and-ordered-acceptance-commands.zh.md)把卡片控件由一组复选框改为「已选顺序列表 + 候选勾选」，并把门禁由逐命令计数收紧为按配置顺序逐条要求。
- **后续变更** [交付纪律以模型判定替换关键词分级](../architecture/2026-09-17-model-graded-delivery-tiers.zh.md)删除了本 note 记下的强/中/弱信号标签编辑器与 `TagField` 的用途之一：分级规则改为一段可编辑文本 `gradingPrompt`，用多行控件渲染。

## 测试

`packages/delivery/tool-delivery/tests/tool-delivery.spec.ts` 覆盖门禁行为：未留记录时阻止、留下记录后放行、逐命令计数（一条记录不足以放行两条命令）、选中命令已不存在时报告、未勾选命令时自由通过、空命令名在注册前被拒绝、L2 结构校验失败仍阻止、L2 结构校验仍按 change id 定向执行。`packages/client/ui-settings-plugins/tests/` 覆盖卡片呈现与控件：游离字符断言（已确认去掉修复即失败）、描述与帮助链接同行、两列栅格与整行控件（已确认去掉整行声明即失败）、标签编辑器的增删与重复拒绝、验收命令候选的渲染/勾选/只读禁用/空态/已消失命令仍可移除，以及控制器对候选与草稿的投影。
