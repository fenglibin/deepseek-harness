# Agent Note: 一张提供方卡片、一个弹窗、一种宽度

Status: implemented

## Problem

Models 设置页面上，同一个编辑器有两个不同的「家」。**添加模型**以弹窗覆盖在分区之上——这是[一个添加模型弹窗](2026-09-02-models-add-dialog-and-picker-defaults.zh.md)刻意做出的决定，目的是让新增提供方不再与行列表争夺纵向空间——而**编辑**则把同一个 `ProviderEditor` 展开在它所编辑的那一行*内部*。于是页面仍然会在操作者脚下生长，只是只剩编辑路径如此；而且卡片的布局取决于用户从哪扇门进来：同一条模型行在弹窗里是并排布局，在行内则会折行。

弹窗的宽度规则从未生效。`ModelsSection.module.css` 给 `.addDialog` 写了 `max-width: 560px`，但 `Modal` 自己的 dialog 规则是 `width: min(380px, 100%)`，而它的 `overflow: hidden` 会把 flex item 的自动最小尺寸归零，因此确定的 380px 宽度胜出：两张提供方卡片无论规则写得多宽，都按原语的默认宽度渲染。没有任何检查能发现这一点——class 挂上了，样式表加载了，唯一的症状只是一张看起来过窄的卡片。

## Decision

**编辑**以弹窗形式打开卡片。`EditProviderDialog` 用同一个 `Modal` 渲染同一个 `ProviderEditor`，标题复用 Edit 按钮作为无障碍名称所用的同一条 `editProvider` 文案，因此朗读按钮的屏幕阅读器会用同一个名字找到它所打开的卡片。行仍然是行：列表是行的列表，卡片不再是行的展开态。

**两个提供方弹窗共用一条宽度规则，声明为 `width: min(570px, 100%)`。** 用 `width` 而不是 `max-width`，因为只有 `width` 能覆盖原语那个确定宽度；570px 是用户实际看到的宽度（380px）加上他要求的 50%。`.addDialog, .editDialog` 与 `.addDialogContent, .editDialogContent` 写成一对规则而非两条，这样两张卡片不可能各自漂移。`styles.client.spec.ts` 钉住这条声明：规则必须设置 `width`、不得退回 `max-width`，且两个弹窗必须一致。

**`settings.models.provider-card` 席位随卡片走。** 弹窗已打开的那一行在弹窗内分发该席位，而不是在行上，因此扩展区在卡片所在的任何位置都只渲染一次。两处都分发会让某个注册方的 UI 在同一个提供方上出现两次。

**首次运行姿态会自行打开同一个弹窗。** 密钥未在任何位置配置、且没有其他行使其变得不必要的整分节提供方，仍然无需点击就呈现它的卡片——现在是同一个弹窗，而不是第三种卡片——而关闭（**取消**、弹窗右上角的关闭，或 Escape）属于该卡片自己：该提供方的其余会话时间退回普通行，并通过**编辑**再次打开。一次只打开一张卡片，因此去点**添加模型**会关掉姿态自行打开的那张卡片。

**刷新丢掉某行时，该行的卡片随之关闭。** 弹窗每次渲染都从合并后的行中解析自己那一行；推送的失效通知或重新加载若移除了该路由，就不会留下卡片去编辑一个目录已不再列出的路径。

## Alternatives considered

**只加宽添加弹窗，编辑保持行内展开。** 否决：它为一个编辑器保留了两套布局，并让页面在编辑路径上继续生长——而这正是添加弹窗当初要消除的生长。它还让行的高度取决于用户上一次点了什么。

**把 `max-width` 调成更大的数字。** 否决：这不会改变任何东西。原语声明的是 `width`，更大的 `max-width` 依然无效，卡片仍是 380px——修复必须是 `width`，样式表测试现在也这么断言。

**以声明值 560px 为基准计算新宽度（→ 840px）。** 被需求否决：用户指明的基准是屏幕上的宽度。570px 是该宽度加 50%；840px 会是用户所见宽度的 2.2 倍。

**去掉首次运行卡片，让行自己提示。** 否决：它移除了本页给「无法触达任何提供方」的用户的唯一提示，而引导接管流程只覆盖官方 DeepSeek 路由。把卡片弹窗化既保留了提示，又消除了第三种卡片。

**给 `AddModelDialog` 增加一个编辑阶段来复用。** 否决：添加弹窗是两张卡片之前的选择器，自带来回跳转；编辑卡片没有需要提供的选择。加一个阶段只会给一个仅为承载选择器而存在的状态机增加分支。

**用提供方显示名称作为弹窗标题。** 否决：弹窗的无障碍名称应当是打开它的那个动作，正如**添加模型**以其按钮命名添加弹窗。`editProvider` 文案已经同时携带显示名称与路由 id，因此在弹窗内隐藏编辑器自己的标题不会丢失任何信息。

**行上也继续分发卡片席位。** 否决：一行出现同一个 keyed 席位的两次分发，会让某个注册方在同一屏上渲染两次。席位是按卡片计的，而卡片在弹窗里。

## Consequences

编辑路径现在像添加路径一样，在设置弹窗之下嵌套了第二层模态框；代价是它后面的行在卡片关闭前不可触达，首次运行卡片打开时**添加模型**也在其中。关掉那张卡片只需一次点击，且本次会话会记住这次关闭。

提供方卡片席位换了承载面，因此以某适配器家族 namespace 注册的注册方，在该行卡片打开时改由弹窗接收该席位，而不是行；分发键、owner props 与「一张卡片一次」的保证均未改变。

两条 e2e golden 现在把编辑器钉为弹窗——`models-settings/declared-edit.expected.md` 与 `onboarding-deepseek-config/models.expected.md`——它们都以弹窗的无障碍标签定位，而不是取页面上恰好先渲染的那个 dialog，因为被 portal 出来的弹窗是设置弹窗的兄弟节点，而非其后代。
