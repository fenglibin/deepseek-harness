# Agent Note: 思考过程跟随响应语言指令

Status: implemented

## Problem

`zh` 响应语言指令管的是「人会读到的散文」：解释、计划、进度、总结、提问，以及模型撰写的提交信息、报告、文档正文与代码注释。它没有提到思考通道，于是中文会话里出现了一个稳定的错配——页面上是中文回答，思考过程却是整段英文推理。

这个错配不是措辞疏漏，而是早先一次有意的排除。该指令的[注释条款改动](2026-09-11-code-comments-follow-response-language.zh.md)把「连思考语言一起强制」列为否决项，理由是思考内容由模型自有、提示词段落无法可靠规定它。那条理由针对的是**可靠性**，而诉求是**方向**：一段概率性生效的指令即便不能保证，也能显著改变英文推理出现的比例，这与注释条款本身所处的状态并无不同——harness 同样不检查产出文本的语言。

## Decision

`zh` 指令新增一句思考语言条款，位置在散文条款之后、注释条款之前：

> 你的思考过程也用中文，包括推理、计划、自检与取舍说明，不要先用英文推理再转述成中文。

条款点名思考通道涵盖的四类内容，并显式禁止「先用英文推理再转述」这一种具体行为——它是模型在中文会话里最常见的退化形式：指令只约束了最终正文，模型于是把思考当作内部草稿留在英文里，再翻译一次交付。

`en` 与 `off` 的语义不变：两者都不注册段落，本次没有引入对侧的英文指令文本。

## Alternatives considered

**维持否决，不改指令。** 否决：这是本次改动要推翻的结论，理由见 [Problem](#problem)。可靠性与方向是两件事，用前者否决后者等于放弃唯一可用的杠杆。

**把思考语言单列成一个段落。** 否决：`SECTION_ORDERS` 会增加一个位置，而两段都由同一个语言解析结果驱动，拆开只会让集中顺序表、测试与 README 多出一个维度，收益要等到出现「正文一种语言、思考另一种语言」的真实需求时才存在。

**在 `Config` 上增加 `reasoningLanguage` 字段。** 否决：部署方没有任何理由让思考与正文使用不同语言；一个没有当前消费者证据的配置面，只会带来 config-catalog、包 README 与 Model Experience 门禁的同步负担。

**只在 persona 里加一句。** 否决：persona 是部署自有文本，语言归属属于 row（见 [The deployment names the language the model answers in](2026-09-02-deployment-response-language.zh.md)）；写进 persona 会让每个部署各自维护一份，且 `minimal` 预设之外的会话不再自动获得。

## Consequences

中文部署的思考通道现在收到同一条语言约束：Web、headless、ACP 与 SDK 会话都随 `dsh-base` 携带该段落，子智能体通过全局层合并收到它。指令字符数从 282 增至 324，约 200 个 token；只要解析出的语言不变，文本就保持稳定，不破坏前缀复用。

生效是概率性的，指令不改变 harness 不检查产出文本这一事实。长工具链上的思考仍可能回到英文，尤其在模型续写自己此前英文推理的会话里——那是边界，不是遗漏，已记入包 README 的已知限制。

该指令是 `RESPONSE_LANGUAGE` 位置上的一个段落，随 `dsh-base` 发布，因此 Web、headless、ACP 与 SDK 会话都携带它；`language` 的默认值随后固定为 `zh`，使这条指令无需配置即存在（见[中文是回复语言的默认值](2026-09-14-chinese-is-the-response-language-default.zh.md)）。

## Testing

- `response-language.spec.ts` 新增一条用例，断言指令包含思考语言条款与「不要先用英文推理再转述成中文」；整个包 20/20 通过（含 Loader 真实组合用例）。
- `loader.spec.ts` 比对 `directiveText('zh')` 而非硬编码文本，不受影响。
- `run-oxlint.ts` 对改动包 0 警告 0 错误。
