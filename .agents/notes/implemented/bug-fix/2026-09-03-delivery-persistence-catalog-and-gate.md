# Agent Note: Delivery discipline — persistence catalog and advance gate fixes

Status: implemented

English | [中文](2026-09-03-delivery-persistence-catalog-and-gate.zh.md)

## Problem

A second deep self-check of the delivery-discipline subsystem against the [design](../../../../docs/design/delivery-discipline-rationale.md) found the domain, fold, projection, state machine, CAS, tiering, post-hooks, and client dock correct under end-to-end probes, but surfaced two defects the earlier self-check missed:

1. The `delivery/change` session event was never registered as a known event type. The `KNOWN_SESSION_EVENT_TYPES` set (generated by `scripts/gen-persistence-catalog.ts`) drives the persistence read path's unknown-type refusal: a persisted log containing a type outside the set and not marked `ignorable` is refused on reload. Because `delivery/change` was missing from that set, any session that used the delivery discipline would fail to resume — the exact opposite of the design's "state survives session resume" promise. The tool catalog and config catalog had been regenerated for the new capability, but the persistence catalog was missed.
2. The `advance_delivery_task` gate reported a misleading record prerequisite for a phase outside the task's level order. Advancing an `l0` task to `designed` (not in the `l0` order) returned "at least one design record is required" instead of the domain's precise "invalid transition", sending the model to fix the wrong thing.

## Decision

Close both defects without touching the deferred cross-capability work.

- Add `delivery/change` to `packages/core/session/src/known-event-types.ts` and its catalog row (`### delivery/*`) to `docs/persistence-catalog.md`, matching what `gen-persistence-catalog.ts` produces for the `SessionEventMap` merge in `packages/delivery/delivery/src/domain.ts`. The event stays log-only (not a surface type) and is a required, known type — not marked `ignorable` — because its loss would corrupt the delivery projection.
- `gateAdvance` now returns the record prerequisite only when the target phase is the single legal next phase (`nextDeliveryPhase(view.level, view.phase)`); any other target falls through to the domain, which rejects it with `DELIVERY_INVALID_TRANSITION`.

## Alternatives considered

**Mark `delivery/change` `ignorable: true` instead of listing it.** Rejected: `ignorable` means the event's loss cannot affect reconstruction, but the delivery projection depends on every `delivery/change` event, so it is a required known type. In-repo events follow the known-types mechanism; `ignorable` is for downstream events this build does not understand.

**Leave the gate message as-is.** Rejected: a gate that names the wrong prerequisite reopens the "model chases the wrong fix" failure mode the discipline exists to close.

## Consequences

- **Bought** session resume for delivery-using sessions (the persistence read path now accepts `delivery/change`), and a precise transition error for out-of-order advances (127 delivery unit tests, 100% coverage; the new "invalid transition, not a record gate" case pins the fix).
- **Cost** a manual edit to two generated files (the generator cannot run in this environment because stale compiled `.js`/`.d.ts` artifacts shadow `src/` sources); the `.zh.md`/`.i18n.yaml` translation of the persistence catalog remains to be regenerated by `doc-sync`.
- **Observed, not changed** — the record tools commit the durable event before appending the `.dsh`/`openspec` artifact, so a filesystem write failure leaves the event committed without a disk file. Commit-first is deliberate: it avoids orphan artifact entries on the more common stale-revision path, and the session log is the authority; the disk file is a projection.
