# Agent Note: 历史分页保住锚点，并让被选中的消息一定落位

Status: implemented

[English](2026-09-05-chat-paging-pick-settle.md) | 中文

## Problem

`ChatView`（`packages/client/ui-chat/src/client/chat/ChatView.tsx`）为两类读者分页加载更早的历史：滚到列表顶部的读者，以及从用户消息抽屉里挑一条的读者。若被挑中的轮次不在已加载窗口内，视图会记下一个待定跳转并持续翻页，直到那一轮的行渲染出来。两个缺陷让读者停在原地。

从底部发起的跳转永远落不了位。重新进入一个没有保存位置的会话会把读者钉在底部。请求在途时，列首会长出「加载中」行，引擎会上报补偿后的位置，而滚动处理器把这个已送达的位置读成"读者又在跟随了"：at-bottom 分支清掉了 `anchorRef`，`toBottom` 在回弹时又清了一次。而 prepend 分支——唯一负责恢复位置和结算跳转的代码——只在锚点仍被持有时才运行。没有锚点，那个终于把目标消息带进来的分页既不恢复也不结算，读者于是看着滚动条一页页变短，却始终到不了自己挑中的那条消息。

这个仍被持有的跳转随后劫持了之后的分页。分页 effect 在目标行渲染出来后就停止翻页，却既不结算也不退役这个跳转，因为结算只存在于 prepend 分支里。此后每一次 prepend——读者往上方翻更早的历史——都会找到这个过期的待定跳转，把读者滚回它所在的位置；这正是手动上翻无法越过那条被挑中消息的原因。

恢复位置本身也会偏高一个「加载中」行。分页到达时请求仍在忙，因此度量发生在「加载中」行还在列里的那次提交，而它会在下一次提交离开，把所有行整体抬高它自身的高度。

## Decision

`pagingRef` 标记一次 prepend 尚未落地的历史请求。在途期间，底部钉住相关的簿记不再丢弃锚点：`toBottom` 与滚动处理器的 at-bottom 分支都保留它；观察到请求结束却没有 prepend 的 effect 才丢弃它；「回到最新」控件则同时放弃锚点与待定跳转，因为主动要求回到底部的读者已经取消了这次跳转。

`promisedRef` 保存一次恢复所承诺的行与偏移。观察请求结束的那个 effect 重新读取该行，而不是减去一个记录下来的高度：各引擎行为不同——Chrome 与 Firefox 自己会做 scroll anchoring，Safari 不会——重新读取按列实际移动的量来校正，在引擎已经补偿过的场景下则是一次空操作。

`settledPendingRef` 持有一份结算闭包，由 prepend 分支与分页 effect 共同读取。只要目标行存在，跳转就结算，无论那一行是怎么来的。prepend 分支只在请求不再忙时结算，因为落页的那次提交里「加载中」行仍在列中，会让目标行高出一个「加载中」行的高度；分页 effect 则在请求结束、列不再移动的那次提交上结算。同一个 effect 还会退役那些任何分页都带不进来的跳转，而不是让它继续持有、等待后续 prepend 去执行它。

## Alternatives considered

**只由分页 effect 结算。** 否决：prepend 分支在绘制前结算，因此目标已在已加载窗口内的跳转不会经过中间帧。全部交给被动 effect 会先绘制恢复后的位置，再跳一次。

**让 prepend 分支在请求仍忙时结算。** 否决：那次提交上「加载中」行还在列里，结算会少走它的高度，并且在请求结束前一直是错的。

**在读者的下一次滚动时退役跳转。** 否决：分页过程本身就会送达滚动位置；读者在目标加载期间轻推一下滚动条就会静默地丢掉自己发起的跳转。

**记录「加载中」行的高度，在请求结束时减掉。** 否决：在自带 scroll anchoring 的引擎上会重复校正。重新读取被锚定的行，度量的是实际发生了多少变化。

**为一个日志里根本产不出来的跳转继续翻页。** 否决：它把请求花在一个永远渲染不出来的目标上，而这个仍被持有的跳转正是让后续 prepend 把读者往回滚的原因。

## Consequences

从抽屉里挑一条用户消息，会一路翻页到它，并把它落在距滚动口顶部一个滚动边距的位置——无论读者此前被钉在底部还是正在历史中段阅读。之后的手动翻页保留读者自己的锚点，而不是弹回早先挑中的那一轮。恢复位置在「加载中」行到来与离开的整个过程中都守住它承诺的偏移。

`packages/client/ui-chat/tests/chat-view.client.spec.tsx` 里新增的两条回归用例按视图真正看到的提交顺序驱动——请求在途、分页落地、请求结束——并配一套从实时 DOM 推导每个矩形的脚本化行布局，断言结算偏移、抽屉的高亮行，以及后续手动翻页时读者的位置保持不变。

既有用例 `pages until a picked user message renders, then settles on it` 从未真正走过"已加载轮次集合变大"这条路径：它在各页之间共用 fixture 的 timings 映射，而共用 timings 映射会复用上一个时间线，于是任何分页都无法新增轮次，被挑中的跳转也就永远无法变为可加载。该用例现在为每一页传入各自的 timings 映射。
