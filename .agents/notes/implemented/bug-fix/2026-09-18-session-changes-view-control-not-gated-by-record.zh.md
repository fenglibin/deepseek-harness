# Agent Note: 变更列表的行控件不再被宿主记录整体门控

Status: implemented

## Problem

输入框上方「变更」列表的每个文件行上，「查看变更」图标在真实使用中完全不出现。列表、路径、「接受」都正常，只有这一枚图标缺失，看起来像功能从未接线。

根因是逐行门控：`SessionChangesPanel` 用 `onViewDiff !== undefined && hasRevision(change.path)` 决定是否渲染该按钮，`hasRevision` 读的是宿主 `list` 动词报告的修订记录集合。不满足时**整块不渲染**——既不是禁用，也没有任何提示。

而两侧数据的生命周期本来就不同：列表读 `changedFiles` 投影（可从完整持久日志重建），修订记录活在 `session_file_revisions` 存储域里（只能靠 `tools/post-execute` 在进程内存中捕获并落盘）。现场取证确认了这个差距是真实且大面积的：`~/.dsh/storages/` 下 `session_file_revisions` 目录在一次真实的 `write` 调用之前根本不存在，而同一工作区此前的会话里已有十余次成功的 `write`/`edit`，`changedFiles` 投影明确列着那些文件。也就是说，那些会话的每一行都没有记录，每一行都因此没有图标。

读者从界面上完全无法区分两种情况：「这个文件没有可对照的版本」与「这个功能坏了」。这正是门控的设计意图（不给一个点开必然失败的入口）与实际体验之间的落差——把控件藏起来并没有消除那个失败，只是让它变得不可见。

## Decision

**「查看变更」对每一行都提供，「撤销该文件」保持逐行门控。**

两个动作在这件事上本就不同类：查看是只读的，撤销会写盘。撤销对一个没有基线的路径无法兑现承诺，因此继续只在宿主记录了该路径时出现；查看则不需要基线就能给出有意义的回答。

## 无记录的路径由视图自己说明

视图此前把任何读取失败都渲染成宿主的原始诊断文本。现在它走 `revisionFailureText(cause, t, 'diff.viewerFailed')`，于是宿主稳定的 `session-revisions/unknown-path` 码映射成本会话没有记录该文件的改动，未映射的码仍保留宿主原文并冠以视图自己的标签。这条映射本已存在于 dock 的撤销路径，视图此前是唯一没有用它的一方。

## 行不再标示写入还是修改

每行原本还有一个「写入」/「修改」标签（`.operation` 样式块与三个 locale 键）。列表本身已经叫「变更」，逐行再贴一个操作种类是冗余噪音，而且它占据横向空间——真实窗口宽度下正是操作图标被挤掉的地方。移除后，一个文件在本会话里是新建还是改写由「查看变更」的两栏对照回答，那是回答这个问题的正确位置。

## Alternatives considered

**保持门控，但把无记录显式化成一个淡色提示。** 诚实，但读者仍然点不开那些文件——用一个可见的「你不能看这个」换掉一个不可见的「你不能看这个」，没有恢复任何能力。

**两个图标都常驻，点下去各自报错。** 界面一致，但为撤销制造入口：它会写盘，而一个没有基线的路径上它只能失败。查看可以常驻正是因为它是只读的；把这个理由一并套到撤销上就丢掉了它。

**无记录时从工作区 git 对象取基线，真正恢复查看与撤销能力。** 这能让历史会话的文件重新可操作，是唯一"治本"的选项。否决于范围：它需要新增一条基线来源、其失败语义（文件从未入库、工作区不是仓库）与配套测试和文档，属于另一个变更的体量；而且它仍然无法覆盖未提交改动。本 Note 记录的是门控本身的修正，与基线来源是否扩展无关。

## Consequences

收益：缺失图标这一现象消失——现在每一行都有「查看变更」，点开后得到一句关于自己处境的说明。行更紧凑，横向空间让给了操作图标。

代价：对无记录的路径，读者要点击一次才知道这个文件不可对照；这是有意的取舍，因为静默隐藏让他连"可以问"都不知道。视图的失败路径现在同时承担"真的坏了"与"这个文件没有记录"两种语义，靠错误码区分。

## Testing

- `packages/client/ui-session-changes`：137 项。（1）列表里有路径但宿主无记录时，「查看变更」仍在且点击发布视图请求；（2）同一情形下「撤销该文件」不出现；（3）宿主 `list` 整体失败时「查看变更」仍在，两个撤销控件都不出现；（4）视图对 `unknown-path` 码渲染那句无记录说明，对未映射错误保留宿主原文并冠以视图标签；（5）`revision-view-control.client.spec.tsx` 用**真实会话日志与真实 `changedFiles` 投影单元**驱动 dock，断言宿主对全部路径都无记录时两行各有一枚眼睛、撤销控件不出现、行上无「写入/修改」标签，且点击第一行发布指向该文件的视图请求。
- 反向验证：把 `hasRevision` 门控加回「查看变更」后，(1)(3) 两条立即失败，证明它们锁住的是门控行为本身。
- `npx tsc -b tsconfig.client.json`、`verify-client-ui-i18n`、`verify-doc-budgets`、`verify-package-readme-limitations`、`verify-package-invariants` 均通过。
