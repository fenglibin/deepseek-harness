# Agent Note: 按循环实例复用已证明的消息冻结

Status: implemented

## Problem

循环在每次构造请求时对**整段派生历史**执行一次 `deepFreeze`。该函数是迭代式全图遍历（显式栈加 `WeakSet` 去重），而长工具对话里消息数量线性增长，于是每轮的遍历成本随历史长度增长：实测请求消息数为 1、3、5、7、9 时，遍历节点数为 7、15、23、31、39。

派生历史本身并没有变化：`Session.deriveMessages()` 按 surface 节点增量缓存，返回新数组但共享同一批 `Message` 对象。也就是说同一批对象被反复完整冻结，而这些工作没有产生任何新的保证。

## Decision

`ReactLoopAgent` 持有一个 `private readonly frozenMessages = new WeakSet<Message>()`。构造请求时先 `deepFreeze(header)`（本地 header 每次请求都重新冻结，因为它的值随组装变化），再逐条检查消息：已在集合中的跳过，否则深冻结并把对象身份加入集合。最后 `Object.freeze(boundaryMessages)` 与 `Object.freeze(...)` 冻结消息数组与请求包装对象；取消信号保持可变。

判据是**对象身份**，不是 `Object.isFrozen`。浅冻结的根对象不能证明其后代已冻结，恢复路径会接管未冻结的对象图，而替换操作（压缩）可以保留消息 id 却改变对象身份与内容。只有"对这个精确对象完成过一次完整遍历"才构成证明。用 `WeakSet` 而非 `Set`，使被替换掉的历史不被该集合留住。

效果：遍历节点数从随历史线性增长变为每轮恒定。同一测量下，5 轮的遍历量是 7、11、11、11、11——增量只覆盖本轮新增的两条消息。

## 曾考虑的替代方案

**用 `Object.isFrozen` 判断是否已冻结。** 不予采用：浅冻结的根对象仍可能包含可变内容；恢复路径接管的对象图未必被深层冻结；替换操作保留 id 时对象身份已变但可能仍带冻结标记。只有按身份记账才成立。

**按消息 id 缓存冻结证明。** 不予采用：替换操作保留 id 的同时改变对象身份与内容，按 id 命中会放过未冻结的新对象。

**用 `Set` 而非 `WeakSet`。** 不予采用：`Set` 会长期持有已被替换或压缩掉的历史对象，把短命历史变成长期留存。

**只冻结新增消息，而不冻结请求包装与数组。** 不予采用：派发的请求必须是不可变的，否则下游适配器或监听器可以改写正在流式传输的请求面。

## 后果

请求构造的深冻结成本从"随历史长度增长"降到"随每次新增消息数增长"，长会话的每轮开销不再累积。代价是循环实例多持一个 `WeakSet`，其条目随对象被回收而消失，因此不构成内存增长。

证明的正确性依赖"消息对象在派生中复用身份"这一既有事实：若将来 `deriveMessages` 改为每次构造新对象，该优化会退化为每次都重新冻结，但不会产生错误行为。

## Testing

`packages/core/agent-loop/tests/request-freeze-reuse.spec.ts` 三条用例：在真实循环上跑 5 轮并用 `deepFreeze` 的 spy 统计每轮遍历的节点数，断言历史确实增长（请求消息数为 1、3、5、7、9）而遍历量恒定；断言派发的请求被完整冻结且取消信号可变；断言同一批消息在两次请求间是同一对象而在尾部追加了新对象。

该套件已验证为有效守卫：把优化从源码移除后第一条用例失败，恢复后通过。
