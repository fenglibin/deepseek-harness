# 交付纪律自动触发方案

> 状态：提案，待用户确认（尚未写任何代码）
> 目标读者：维护者
> 关联：[交付纪律方案](delivery-discipline-rationale.zh.md)，其 B1–B5 批次已交付任务域、阶段状态机、产物持久化、后置命令与客户端 UI。本文档补齐这些批次留下的唯一缺口：没有任何东西自动启动这套纪律。

---

## 1. 背景与动机

[交付纪律方案](delivery-discipline-rationale.zh.md)在第 1 节写明了自己的核心原则：*流程约束不能只依赖 LLM 自觉，必须由程序强制执行*。B1–B5 批次交付了"程序化"的那一半——`DeliveryTask` 域、前向状态机、`record_*` 工具、`advance` 门禁、后置命令——但其中每一项都只有在模型自愿调用 `create_delivery_task` 之后才会生效。没有任何程序化机制去检测一个大需求并启动任务，所以模型可以（也确实会）通过干脆不创建任务而绕过整套纪律。

一次真实会话证明了这一失效。一个大需求（"处理图片与文字混合输入"）走了 `brainstorming` 技能、向用户问了两轮 `ask_user_question`、并用 `write` 工具把设计文档直接写到 `docs/design/` 下。整个会话里 delivery 工具只被调用了一次——`get_delivery_task`，返回 `{ task: null }`。`create_delivery_task`、`record_design`、`record_spec`、`record_change`、`advance_delivery_task` 各自调用次数为 0。设计文档落在了 `.dsh/design/` 之外，agent 最后问"要不要现在开 delivery task"，把纪律当成了可选的下一步，而非默认动作。

同样的"仅靠提示词"模式也统治着相邻的 `goal` 能力：`create_goal` 的描述写着模型"可以推断该意图"，但没有任何东西强制它。本文档不重做 `goal`；它只是给交付纪律补上它自己的原则所要求的程序化起点。

---

## 2. 目标

- **自动发现**大需求并创建交付任务，无需模型记得去做。
- **自动校验**针对实际存在的产物做完整度校验：当任务带有设计记录或 spec 记录时，到达 `accepted` 需要一次程序化检查确认实现覆盖了它们；没有这类记录的任务不被拦截，纪律因此绝不卡住普通工作。
- **默认开启后置闸**：内置一个非空的 `postHooks` 基线，让"验收跟随验证"开箱即用。
- **验收时自动记录变更**，让每个完成的任务即使模型忘了 `record_change` 也留下变更记录。

---

## 3. 非目标

- 不改变 `agent-loop` 本身（遵循"Plugins, not loop changes"）；启动钩子复用既有事件。
- 不重新规定阶段状态机或 `record_*` 工具；它们按已交付状态是正确的。
- 不约束子代理或 workflow 子任务；根 agent 的任务仍是唯一作用域。
- 不判断实现是否*语义正确*；完整度检查验证的是*对已记录产物的覆盖*，而非业务正确性（后者仍归后置命令与测试负责）。

---

## 4. 现状

已交付且可用：`DeliveryTask` 域、前向阶段顺序、`delivery` 投影、六个模型工具、到 `.dsh/` 与 `openspec/` 的产物持久化、后置命令、客户端时间线卡片与浮动卡片。

仍有四个缺口，全部落在"起点"与"终点"两端：

| 缺口 | 证据 | 后果 |
|---|---|---|
| 无自动发现 | `create_delivery_task` 只会被模型调用；`inferLevel` 只在它内部运行 | 大需求运行时没有任务、没有分级、没有门禁 |
| 无完整度校验 | `gateAdvance` 只检查 `designed`/`specified`/`implemented` 的记录数；`verified` 无前置条件 | 任务可以在 design/spec 记录存在但未实现的情况下到达 `accepted` |
| `postHooks` 默认空 | `Config.postHooks` 默认 `[]`；预设只设了 `enforcement: stateful` | 验收默认不跑任何验证命令 |
| 无自动变更记录 | `record_change` 仅是模型工具 | 若模型忘了，已完成任务可带着 `changeCount === 0` 到达 `accepted` |

## 5. 候选方案

### 方案 A：在 `agent/pre-step` 自动创建（推荐）

一个 `agent/pre-step` 的 waterfall 监听器读取会话当前的 delivery 任务；当不存在任务且已领取的人类消息达到规模 proxy 时，在步骤继续前创建一个 `l1`/`l2` 任务。这正是 `compaction-basic` 与 `plan-mode` 已经用来注入持久材料的同一事件，模式已确立，且创建的任务可从会话日志重建。

- **收益**：纪律无需模型配合即可启动；分级由真实消息文本（而非估算）驱动。
- **代价**：`pre-step` 每一步都触发，监听器必须幂等且廉价；创建任务是一次持久追加，与 `plan-mode` 的写入方式一致。

### 方案 B：在消息准入处（会话控制器）自动创建

在 `session-controller.prompt()` 里，当人类消息到达且不存在任务时创建任务。

- **收益**：创建正好落在"用户提交了需求"这一边界。
- **代价**：会话控制器是 API 平面；delivery 是宿主平面域，且一个需求可能在规模可确定之前跨越数条消息。这还把 API 层耦合到了宿主服务上。

### 方案 C：仅强化系统提示词（对照组）

改写 `guidance()`，命令模型对大工作立即创建任务，不改代码。

- **收益**：零代码、零风险。
- **代价**：会话证据已经证伪了这一点；模型忽略了既有指令。它违背了方案自身的核心原则。

### 方案 D：在 `agent/turn-stopping` 软提醒

不创建任务；在轮次结束时检测"有实质工作却没有任务"，注入提醒上下文。

- **收益**：从不打扰探索。
- **代价**：提醒不是启动；模型可以像今天忽略提示词一样忽略它。

**决策**：起点采用方案 A，外加两处终点侧补充——`accepted` 的完整度门禁与一个非空 `postHooks` 基线。方案 C、D 被否决，因为它们重新引入了核心原则所禁止的"LLM 自觉"。

## 6. 推荐方案

### 6.1 自动发现与自动创建

一个新插件（或对 `tool-delivery` 的扩展）在 `agent/pre-step` 上注册 waterfall 监听器。每一步它解析调用 agent 的会话与当前 `ctx.delivery` 视图：

- 存在当前任务，或已领取消息不携带直接人类请求 → 不做任何事（落到 `next()`）。
- 无当前任务且存在直接人类请求 → 把拼接后的请求文本对照 `designThreshold`/`openspecThreshold` 度量，用推断的分级与请求文本作为 objective 调用 `ctx.delivery.create()`，然后落到 `next()`。

创建的任务立即出现在既有的时间线卡片与浮动卡片中；无需新 UI。分级沿用 `create_delivery_task` 今天所用的同一 proxy，因此显式偏大或偏小的请求仍可由模型通过既有工具纠正。

### 6.2 `accepted` 的完整度校验

`gateAdvance` 增加一项前置条件：推进到 `accepted` 要求每条 design 与 spec 记录都被实现覆盖。"覆盖"在记录格式允许时是程序化的，否则委托：

- **Spec 记录（l2）** 写入 `openspec/changes/<task-id>/spec.md`；当完整的 openspec `tasks.md` 布局存在时，覆盖意味着每个 checkbox 都被勾选，通过读取文件验证。这是完全程序化的。
- **Design 记录（l1/l2）** 是自由文本，没有可机检的清单。这里的覆盖由模型验证：`advance` 到 `accepted` 返回一个 blocking 错误，列出未验证的 design 记录并指示模型确认每条已实现，镜像既有的 `DELIVERY_GATE_BLOCKED` 流程。该确认是被记录下来的陈述，而非沉默的应承。

design 与 spec 记录均为零的任务完全跳过此检查——正是用户指定的"只校验实际存在的"规则——因此 `l0` 修复绝不停滞。

### 6.3 默认后置闸

预设与 bundle 把 `postHooks` 设为非空基线（例如 `openspec validate --strict` 与 `pnpm run test`），让验收默认运行验证。该字段仍可按部署覆盖。

### 6.4 验收时自动变更记录

当 `advance` 到达 `accepted` 时，若 `changeCount === 0`，工具在提交推进前先记录一条概括 objective 的变更，因此任何任务都不会在没有变更记录的情况下完成。

## 7. 实施批次

| 批次 | 内容 | 验收标志 |
|---|---|---|
| C1 | `agent/pre-step` 自动发现监听器 + 复用规模 proxy + 幂等 | 大需求无需模型调用即创建任务；小修复不创建 |
| C2 | `accepted` 的完整度门禁（spec checkbox 检查 + design 确认） | 带记录的任务在记录被覆盖前无法到达 `accepted`；无记录任务不受影响 |
| C3 | 预设中的 `postHooks` 基线 + 验收时自动变更记录 | 验收运行配置的命令，且每个完成任务都有变更记录 |

每批独立可验证、可回滚，匹配原方案的分阶段纪律。

---

## 8. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 自动创建在琐碎请求上触发 | 小修复被强制进任务 | 复用规模 proxy；低于阈值的请求保持无任务 |
| `pre-step` 监听器开销 | 每一步都有额外工作 | 解析任务一次，存在任务时短路 |
| 完整度检查阻塞合法工作 | 任务无法完成 | 仅在存在记录时运行；模型确认路径是逃生口 |
| 确认路径仍受模型约束 | 模型可虚假确认 | 确认被记录为持久陈述，且后置命令无论如何都会运行 |

**回滚**：C1–C3 是独立的配置/工具补充。禁用自动发现监听器或设 `postHooks: []` 即恢复今日行为；状态机与工具不变。

## 9. 待决问题

这些在实施前需要决定；此处有意只列出而不做决定。

1. **自动发现的挂载点**。`agent/pre-step`（方案 A）还是消息准入（方案 B）。本文档推荐 A。
2. **分级阈值**。复用既有的 `designThreshold`/`openspecThreshold` 字符/todo/文件 proxy，还是为自动启动路径另设阈值？
3. **自动创建任务对用户的可见性**。静默创建（贴合"让用户无感知"）还是在自动创建时给一条简短提示。
4. **完整度检查深度**。对 design 记录，模型确认路径是否可接受，还是必须把每条设计决策都变成可机检条目？
