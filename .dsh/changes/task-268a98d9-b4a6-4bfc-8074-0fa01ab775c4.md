- [revision 14] 修复用户报告的回归：重启后「修改的文件」列表中看不到「查看变更」按钮。按钮没有被删除——它在代码里（SessionChangesDock.tsx:360 的 onViewDiff + hasRevision 门控）依然存在，是被运行时门控掉的。

根因（我上一轮引入的真 bug）：packages/fs/session-file-revisions 的构造函数签名是 (ctx, public config: Config)，而 maxRecordBytes getter 写的是 this.config.maxRecordBytes。当插件条目不传 config 时 this.config 是 undefined，该 getter 抛 TypeError: Cannot read properties of undefined (reading 'maxRecordBytes')。这个抛出发生在 enqueueWrite 的写任务体内，被紧随其后的 fail-soft .catch 捕获后只经 ctx.logger 记一条 warning——因此捕获在内存里照常工作（list 能返回记录），但记录永远不落盘。

关键点是 shipped 装配恰恰就是不传 config 的：packages/bundle/web-app/cordis.patch.yml 的 session-file-revisions 行只声明 id 与 name，没有 config。而我全部既有测试都传了 {}，因此这条真实路径从未被覆盖——这正是它逃过上一轮 1401 个测试与深度自检的原因。

症状链：进程重启 → 磁盘上没有 session_file_revisions 域（实测 ~/.dsh/storages/ 下该目录从未创建，只有 session_projcache 与 workspace.json）→ 恢复的修订集合为空 → client 的 recorded 集合为空 → hasRevision(path) 恒为 false → 每行的「查看变更」都不渲染。同时「全部撤销」也一并消失（同一事实门控）。列表本身照常显示，因为它读的是可从完整持久日志重建的 changedFiles 投影——两者生命周期不同，这正是先前设计说明里写明的那个分歧。

修复：构造函数的 config 改为可选（public config?: Config），getter 改为 this.config?.maxRecordBytes ?? DEFAULT_MAX_RECORD_BYTES；JSDoc 写明「不声明 config 的组合会传 undefined，这是 shipped 形态，因此每个字段都各自解析默认值，而不是从一个可能不存在的对象上读取」。全仓库只有这一处 this.config 读取点（已 grep 确认），另外两个改动包不读 config。

证据（全部本机实测，非推断）：
1. 探针复现：以 shipped 形态（不传 config）装配真实 storage 栈 + ToolRuntime，执行一次 write，得到「list: 1（内存有记录）但磁盘无文件落盘」，且 getter 直接抛 TypeError。
2. 探针确证触发点：包装 domain table 的 put/delete 后确认 PUT 从未被调用，即写任务在到达介质前就抛了。
3. 修复后同一探针：maxRecordBytes 正确回落到 4194304，磁盘出现 nc.json。
4. 新增回归测试「persists with NO config argument, as the shipped assembly declares it」：以 omitConfig 走不传 config 的 durable 装配，写入后 dispose，再以同一 root 重开并断言 list 长度为 1。回退修复后该测试失败、恢复后通过，证明它锁定的是真实行为。
5. 已重建宿主产物（lib/index.js 14:58）并确认编译结果含 maxRecordBytes ?? 4194304 的默认值回落。
6. packages/fs/session-file-revisions 与 packages/api/session-file-revisions 共 64 个测试通过；受影响范围 verify-changed 1691 通过 1 跳过。

教训与后续：这类缺陷的形态是「fail-soft 的 catch 把编程错误当成可容忍的运行故障吞掉」。安装态装配（不传 config）与测试装配（传 {}）不一致时，测试套件会系统性地漏掉这一类。已把该形态固化进回归测试；未做的是让 catch 区分「写入故障」与「代码缺陷」——例如对 TypeError 一类编程错误不吞，这属于 fail-soft 策略的取舍，需要单独决策，本轮未擅自扩大改动。
