三、业务正确性——**发现并修复的真实缺陷**
初始实现按"delivery-tasks 清单非空"决定是否采用权威清单，否则回落 todos。自检用完整装配（ToolRuntime + SystemPrompt + UserQuestionService + AgentRegistry + SessionProjectionRegistry + DeliveryService + ToolTodo）重放后，探针输出显示两侧在 l0 与 l2 下**仍然不一致**：
  [l0] 左侧= null（浮层显示「待拆分」）  右侧= ["in_progress:小修一","pending:小修二"]
  [l2] 左侧= null                        右侧= ["in_progress:l2 当轮"]
根因：mirrorTodos 只对 l1 镜像，l0 的 todo_write 永不进入清单，l2 又禁用 todo_write，因此这两档清单合法地为空，而旧判据会回落显示左侧浮层没有的当轮计划——正是用户报告的"两边不同"的另一个实例。修法：判据改为**会话是否持有交付任务**（读 delivery 投影非 null）；持有任务时清单为空就渲染空列表（左侧此时显示「待拆分」，两侧一致）。这是"能跑通但行为不对"的典型：测试全绿但语义错误。

自检还暴露了一个虚假通过：最初探针的 bench 只挂 SessionProjectionRegistry 与 ToolRuntime，todos 投影因 tool-todo 的 inject 座位不全而根本没注册，读到 undefined 会让"两侧一致"恒真。已改用完整装配重做，并把这一要求写进设计文档与 Agent Note。
