- [revision 3] 深度自检发现的问题清单与修复设计（依 proposal/design D1-D7 与 spec 9 个 scenario）。

## 缺陷 1（阻断级）：`sessionFileRevisions` Remote 命名空间从未挂载 —— 整条功能不可用

spec「展示单个文件在会话中的变更」「撤销保留外部改动」等所有需要 list/diff/revert 的 scenario 在真实 GUI 中全部不可达。

证据：
- 客户端唯一消费点 `packages/client/ui-session-changes/src/client/index.ts:76` 读 `ctx.remote.sessionFileRevisions`。
- 客户端命名空间由 `packages/api/remotes/src/client/index.ts` 的 `apply()` 用 `ctx.remote.$mount(contribution)` 逐个挂载（第 166-172 行的 contribution 列表）。
- 该文件既未 import `@deepseek-ai/dsh-api-session-file-revisions/remote`，contribution 列表里也没有它；全仓 grep `session-file-revisions/remote` 只命中 ui-session-changes 的**类型**导入（`import type {}`，运行时被擦除）。
- `packages/api/remotes/package.json` 未声明该依赖。
- `remoteVerbs()` 直接返回对象、不判 `undefined`（对比 `openFile` 走 `ctx.get('fileViewer')` 的缺席判定），所以未挂载时它返回的 verbs 仍非 undefined → dock 会**显示**「查看变更/全部撤销」按钮，点击后在 `remote.diff(...)` 抛 TypeError。这违反 spec「未装配修订捕获」scenario 要求的「隐藏控件 + 保持列表与接受不变」。

修复：在建言装配里 import 并 `$mount` 该 contribution，并补 package.json 依赖。

## 缺陷 2（数据丢失级）：`before: null` 被无条件当作「会话新建」，撤销会删除并非本会话创建的文件

spec scenario「撤销会话新建的文件」写的是「仅当文件内容仍是本会话写入的那一刻才删除」。

证据：`packages/fs/fs-local/src/index.ts:200-203` 对覆写计算 diff 基线：
```
const diffable = existing !== null && Buffer.byteLength(content,'utf8') < this.config.diffBasisMaxBytes
const before = diffable ? await readTextForDiff(target.targetKey, this.config.diffBasisMaxBytes, signal) : null
```
`readTextForDiff` 对「at/above-limit、binary、non-UTF-8、unreadable」一律返回 `null`（fsio.ts:695-712）。于是对**一个已存在的 12 MiB 文件**做覆写时，write 结果 `operation:'update'` 但 `before:null`——与真正的 create 在结果里完全同形。

`captureMutation` 只按 `typeof before === 'string' ? before : null` 归类，`revertOne` 见 `baseline === null` 就走 `rm(contained)` 删除分支（api/index.ts:149-156）。探针实证：该记录 `baseline === null`，`isCreate === true` → 走删除分支。

修复依据：write 的输出 schema 自带 `operation: 'create' | 'update'`（tool-fs/write.ts:84）。把它作为「是否真的新建」的判据，只有 `create` 才允许 `baseline = null`；`update` 而 `before` 缺失时该记录不可撤销，须显式降级而非删除。

## 缺陷 3：跨会话 seq 不可比，父子合并会取错基线/末态

design D1/spec「子代理的改动归入所属会话」要求父子同改一文件时「基线取更早者、末态取更晚者」。

证据：`mergeRevisions`/`foldMutation` 直接用裸 seq 比较（registry.ts:130-131），但 seq 是**会话本地**的（core/session/src/index.ts:563 `get seq() { return this.log.length }`）。子代理会话经 `childSessionMeta` 以 `parentSession` + `seedLength` 从父日志 fork（child-agent.ts:138-156、continuation.ts:447），其 seq 从 seed 长度起算，与父会话的 seq 属于不同坐标系。

探针实证：父 seq=100 写 base→mid、子 seq=50 之后写 mid→final（真实时间更晚）时，合并结果 `baseline:'mid'`、`endState:'mid'`——基线被取到子会话的 before、末态留在父会话的 mid，该文件的会话改动**整体消失**，显示为空 diff 且撤销无效果。

修复：按「归属会话树」的正确时序比较，而不是裸 seq。父会话自身的事件一定先于其子会话（子会话由父派发后创建），故可用「先按会话在树中的相对序（父先于子），同会话内再按 seq」构成可比顺序；`record` 时把该会话在树中的序一并存入。

## 缺陷 4（次要）：`revert()` 的 path 语义与「全部撤销」在客户端被误用

`revisionsRef.revertAll(changes.map(...))` 传**全部已加载路径**（含已接受者）。该函数在 `paths.length === 1` 时附带 `path`，否则省略 `path` 变成「撤销该会话全部文件」。语义上「全部撤销」本就该撤销整个会话的改动，故行为正确；但 `paths.length === 1` 分支会把「只有一个文件」退化为单文件撤销，且传空数组时静默变成全量撤销，属隐晦耦合。此处保留行为、补注释说明。

## 缺陷 5（次要）：`list`/`RevertOutcome`/`FileRevisionSummary`/`RevisionSize`/`BaselineOrigin` 等导出无消费方

`DEFAULT_DISPLAY_MAX_BYTES`(host) 与 `DEFAULT_MAX_DIFF_BYTES`(api) 是重复定义的同一个 512KiB 上限；`RevertOutcome` 等类型无任何生产消费者。按仓库「Require a current owner and need」，清理无消费者的导出与重复常量。

## 缺陷 6（次要）：未使用的 locale keys

`revertConfirm`、`viewChangesAll`、`revert`、`diff.baseline`/`diff.current`/`diff.empty`（部分）无引用。保留有引用者，删除纯冗余项需评估 `verify-client-ui-i18n` 的字典完整性要求。

## 验证方式
逐 scenario 用可执行测试证明修复前后行为差异：缺陷 1 以客户端装配断言 contribution 列表含该命名空间；缺陷 2/3 补 host 侧行为测试（大文件覆写不被删除、父先于子的合并顺序）；全部回归。
