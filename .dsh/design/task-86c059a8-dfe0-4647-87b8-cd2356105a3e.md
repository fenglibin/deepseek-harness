- [revision 3] 交付纪律改造设计（完整文档：docs/plans/2026-09-16-delivery-discipline-observability-design.md）。

现状结论：
- 分级为两处串联（grading.ts 纯文本扫描 + index.ts 的 inferLevel 叠加模型自报信号）加两条触发路径（autoDetect 仅 l2 自动建任务，l0/l1 只注入 GRADING_RUBRIC 由模型自决）。
- 三级差异仅在阶段序列与少量门禁；关键不对称是 l2 禁用 todo_write、l1 允许。
- verified 阶段实际只做两件事：coverageGap（对 l1 因 changeId 为空串而完全失效，对 l2 仅检查 covers 注解形式）与非 l2 的清单完成度（未调用 record_tasks 时直接放行）。命令级验证位于 accepted 而非 verified。
- 问题 1 根因：DeliveryFloatCard 的 `items.length === 0 ? todos ?? [] : []` 使 delivery-tasks 一旦有记录便不再读 todos，而 l1 下 todo_write 仍合法，故左侧卡片冻结；todos 投影又在每轮 turn/start 清空。delivery-tasks 已算出 progress 但客户端未使用。
- 问题 3 结论：分级/执行/验证已集中在 tool-delivery 一个包；可配置性已实现一半（installPolicy 已注册 settings 的 delivery namespace，用户覆盖实时生效），缺的只是设置卡片。

设计决策 D1-D6：
- D1 l1 保留 todo_write，由 tool-delivery 监听 session/event 捕获 todo/write 并追加持久 delivery/tasks，使 delivery-tasks 成为唯一权威源。
- D2 verified 改为三类输入（原始需求必须、任务列表分级取值、设计文档 l1/l2）+ 四道检查（清单完整性、覆盖性含 l1、产物核验前移 postHooks 与 openspec validate、模型逐条对账原始需求），取代 20 字自由文本放行。
- D3 reviewRounds 由模块级 Map 改为随任务/阶段持久化。
- D4 设置卡片需新增布尔与枚举控件（现仅 numberField/textField）；词表需列表控件或按行解析。
- D5 修正 enforcement: off 的加载期判定与运行期设置变更不一致的现存缺陷。
- D6 进度按阶段分组读 progress、提供常驻入口、展示分级判定依据、合并 LEVEL_PHASES 的 host/client 两份定义。

开放问题：specChars 默认 200 对中文过低且与 README 示例 1200 不一致；强信号词表含高频词易误判 l2；l1 缺确定性产生路径；抽分为三个独立包还是包内分层加客户端设置卡片包。
