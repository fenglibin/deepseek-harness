- [revision 3] 完整设计见 docs/plans/2026-09-16-session-file-readonly-viewer-design.md。

结论：复用已合入的 packages/api/file-browser + packages/client/ui-file-browser（提交 cb0d22a168、5bd5d60088），扩展它支持「带具体文件路径、只读打开」，不新建只读查看器包。

现状形状：它当前是左右分栏的工作区浏览器（左列懒加载文件树，右列内容区文本走 CodeEditor、图片走 img、二进制与超限给提示），入口只有工作区行菜单，且只携带 workspaceId。

D1 扩展点放 ui-file-browser：会话链接需要的内容区正是它已实现的，差别只在打开意图与是否可写；新增第三个注册点与一个服务门面，不做第二套 Modal。

D2 打开意图是判别联合：{kind:'workspace', workspaceId, title} | {kind:'file', workspaceId, path, title, readOnly:true}。判别联合让「浏览工作区却只读」这种无意义组合不可表达；否决给现有 request 加可选 path?/readOnly?。

D3 会话到工作区的解析在客户端完成：WorkspaceView.sessionIds 已把会话登记到工作区，工作区按会话 cwd 分组派生（packages/workspace/workspace/src/index.ts 的 bootstrap），客户端用现有 useWorkspaces 快照按 sessionIds.includes(sessionId) 反查即可，不新增 Host API、不改 Remote 协议。查不到工作区（子代理、已归档）时明确提示，不静默回退 native 打开。

D4 只读是打开意图的属性，不是文件的属性：会话链接一律 readOnly:true，CodeEditor 已有 readOnly 支持，只读态隐藏保存/重载/覆盖，保留复制与高亮。同一文件从工作区菜单进可编辑、从会话链接进只读，这是入口语义。

D5 native 打开降级为查看器内次要入口：仅当 connection.isLoopback 且 session.canOpenWorkspacePath() 为真时渲染。目录路径（产物行「在文件夹中显示」）继续只走 native，不进查看器。

D6 不分页，沿用现有 maxFileBytes（默认 2 MiB）与 too-large 提示。原设计考虑分页拉取，复用现有实现后改为沿用上限：CodeEditor 一次性接收全文并整体 tokenize，分页要求把它改造成窗口化渲染，代价远超收益；超限时给明确提示并保留 native 入口。这是有意收窄。

D7 客户端经 ctx.provide 暴露 openFile 门面：ui-file-browser 在 apply 中 provide('fileViewer', {open})，ui-chat / ui-session-changes / ui-delivery 用 ctx.get('fileViewer') 可选读取，缺席即不提供，与 chatFileMentions 的既有模式一致（packages/client/ui-deliverables/src/client/index.ts）。门面的 open 接收 {sessionId, path} 并自己完成工作区反查；否决各调用点各自反查（三处重复同一段逻辑，且该映射只应有一个归属者）。

影响面：ui-file-browser（门面、第三个注册点、判别联合、只读接线、native 次要入口）、ui-chat / ui-session-changes / ui-delivery（openFile 改走门面）、ui-deliverables（产物行与 chatFileMentions 改走门面，目录路径保留 native）。不新增包，不改 api/file-browser 的 Remote 协议，不改会话日志，模型不可见。
