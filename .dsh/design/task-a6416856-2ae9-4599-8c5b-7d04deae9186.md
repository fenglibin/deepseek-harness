- [revision 2] ## D1 连接校验是一条新的 Host 能力接缝，而不是模型发现的开关

`LlmRuntime` 新增 `registerConnectionCheck(settingsNs, check)` 与 `validateConnection(settingsNs, request)`，外加 `@Remote('validateConnection')`。

`discoverModels` 回答的是“这个提供方有哪些模型”，并且对目录内路由直接用本地目录作答、完全不发网络请求；而“配置是否可用”必须真正打到 endpoint。把校验做成 discovery 的一个开关会让 DeepSeek 官方行得到一个“永远通过”的假结果，所以两者是不同的能力，各自注册。

## D2 探针是一次最小的 hello 调用，不是列表调用

`POST {baseURL}/chat/completions`，单条 user 消息 `hi`，`max_tokens: 1`，非流式。一次请求同时校验 endpoint、密钥和模型 ID——这正是“模型配置可用性”的含义。`GET /models` 会漏掉模型 ID，而且部分网关在未鉴权时也照常返回。

## D3 失败抛 LlmError，成功返回一个小报告

与 discovery 的形状保持一致：失败抛出带原因的 `LlmError`，Remote 适配器包成 `llm/connection-check-rejected`。成功返回 `{ baseURL, model }`，卡片据此说清是哪个 endpoint 的哪个模型应答的。

## D4 两个提供方实现：llm-pi-ai 与 llm-deepseek

两者都是 OpenAI 兼容的 chat completions。

- `llm-pi-ai`：与 discovery 一致，只支持 `openai-completions` 协议，其余协议明确拒绝而不是猜测响应形状；baseURL 依次为草稿 → 已存 profile → 已安装目录；model 依次为草稿 → 该路由解析出的第一个模型。
- `llm-deepseek`：baseURL 依次为草稿 → 插件 config → `PUBLIC_BASE_URL`；model 依次为草稿 → 已配置目录的第一个模型。

草稿未带密钥时，Host 自行解析该路由已存储的密钥（复用 discovery 的 `storedApiKey` 形状），与 discovery 一致——配置界面只持有脱敏描述符，从不持有真实密钥。

## D5 客户端：一个共享的“连接验证”动作挂在 EditorFooter 上

`EditorFooter` 新增可选的 validate 动作，于是添加对话框的两张卡片（`ProviderEditor` 处理选中的目录路由，`CustomProviderCard` 处理手工声明的路由）和编辑对话框（也是 `ProviderEditor`）通过同一个座位拿到它，结果作为卡片内的一行状态渲染。校验用的是草稿值而非已存值，所以未保存的密钥和 endpoint 修改都能被验证。

## D6 “添加模型”进入页头行并右对齐，文案缩短为“添加”

标题与说明留在左侧，按钮移到页头行右侧；文案从“添加模型”改为“添加”，保留 `+` 图标与 `添加` 的可访问名。按钮本体随之缩短。

## D7 命名空间未注册校验时按钮禁用并说明原因

与 `ModelListEditor` 里“获取可用模型”的处理一致：页面从 namespace 视图判断该族是否提供校验能力，没有就把按钮置灰并给出说明，而不是发出一个注定失败的请求。
