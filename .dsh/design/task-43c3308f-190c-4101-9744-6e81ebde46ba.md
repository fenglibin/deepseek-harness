- [revision 6] # 修复 DSH 失败单元测试：判定规则与修复策略

## 目标

把当前失败的单元测试修到全绿，且**区分「测试自身过时」与「产品实现缺陷」**：前者直接改测试，后者改实现（用户明确要求对后者仔细斟酌，不可为了变绿而弱化断言）。

## 判定规则（本次实际执行的分类依据）

对每个失败，先取证「实现应是什么样」，再看测试期望是否与之一致：

1. **测试过时** → 改测试。判据：实现侧有明确规范来源（生成器输出、文档规范、门禁语义），且测试期望的是已被有意移除的行为。
2. **实现缺陷** → 改实现。判据：测试守的是一条仍然成立的契约，而实现违反了它。
3. **环境限制** → 按用户决定删除或改写。判据：把环境条件换成不受限时测试即通过。
4. **并发时序** → 修 harness 机制。判据：单独运行通过、并发下失败，且能定位到具体的竞态机制而非"随机"。

## 关键决策

### D1 中文化遗留一律改测试，不动生成器

根因：提交 `6537426d2d`「修复英文遗留问题」把生成器与门禁中文化（`docs/cordis-api/*.zh.md`、`# 会话持久化事件目录`、`packages/*/README.zh.md`），但该提交 `--name-only` 中**没有任何 spec/test 文件**。因此 4 个 spec 的英文断言全部失准。

改测试而非回退实现：中文化是既定方向（英文文档树已在 `3af6143761`、`66b66c0eef` 删除），断言应跟随。

一处例外：`**Returns**` → `**返回**`。生成器只本地化了标签、正文保留源 JSDoc 原文——`fiber.zh.md` 中确为 `**返回** a disposer that tears the effect down...`。故断言按实际输出修正，而非假定整行都该中文化。

### D2 `verify-subsystem-pages` 的索引排除是真实缺陷，改实现

中文化时把 `page !== 'README.md' && !page.endsWith('.zh.md')` 简化为 `page.endsWith('.zh.md')`，**连带删掉了索引页排除**。实测：group README 只链 `docs/subsystems/README.zh.md` 时门禁误判为合法归属（`{"linked":1,"violations":[]}`）。

这属于「链接到索引 ≠ 声明归属」这一仍然成立的契约被实现违反，故恢复为 `page !== 'README.zh.md'`，并在 JSDoc 记录该排除的语义。spec 中 3 项断言守的正是此语义，属**有效守卫**，保留并只把夹具同步到 `.zh.md`。

### D3 并发 flake 修机制而非放宽超时

`harness.spec.ts` 两项在全量并发下失败、单跑 63/63 通过。读 vitest 源码（`test.DNmyFkvJ.js` 的 `waitFor`）确认机制：**超时若落在某次轮询仍在进行中，`lastError` 仍是上一轮的值或为空，于是抛通用的 `Timed out in waitFor!`，丢弃回调诊断**。实验复现（首次轮询 60ms / 超时 20ms）：确实抛 `Timed out in waitFor!`。

这解释了报错为何是 vitest 的通用文案而非 `did not persist expected inbox message within 20ms`。修法：新增 `waitForPersisted()` 捕获最后一条诊断并在到期时重抛。**不放宽 20ms**——那是测试有意的边界值。

### D4 `verify-changed` 的 self-reference 依赖改为自足夹具

`main` 的 3 个用例断言真实工作树（`run` 必被调用、direct-only 必为子集）。但实现按设计在无包内改动时走 `NO_SCOPE_EXIT_CODE` 跳过，所以这些用例**只在「检出恰好有改动」时通过**——既脆弱又与被测逻辑的真实分支相反。

改为临时 `git init` 仓库夹具：提交两包树（`one`、`two`，后者依赖前者）→ 编辑一处 → 断言确定的目录集合。新增「包外改动即跳过运行器」用例，覆盖原先缺失的跳过分支。

### D5 `tool-delivery` 沙箱用例：按用户指示删除

3 个用例在 `$HOME` 下 `mkdtempSync`，被文件沙箱 EPERM 拒绝；把 `HOME` 指向可写目录后该 spec 111/111 通过。用户明确选择「删除这几个单元测试」。删除整个 describe 块并清理随之失效的导入。

### D6 fixture 布局重写：先证明无损再执行

97 个 `snapshots/**/session*.jsonl` 处于非规范布局。用户先问「是否可删」——取证后给出否定结论：它们是 CI `test:snapshot` 的**回放输入**（`headless.snapshot.ts` 以 `DSH_SNAPSHOT_FILE` 驱动真实子进程），实测删除一个即令 corpus 门禁失败，且本地无 key 无法重录。

用户改为确认执行机械重写。**执行前先证明无损**：用 `parseSessionLog` 比对 HEAD 原始字节与重写后字节，剔除 `seq`/`time` 信封后 97/97 逻辑事件一致，然后才落盘。

### D7 Cordis 目录登记：按同族先例补齐

`fileBrowserController`、`mcpResources`、`skillRoots`、`mcpAuthSink`、`resources`、`workspaceRowMenu` 未登记（fork 新增包引入）。归属依据：
- 可渲染的 Host 服务 → `SERVICE_PAGE`（`filesystem.md` / `mcp.md` / `skills.md`，取最贴近其能力的子系统页）。
- 不可渲染的可选/客户端键 → `SERVICE_WALK_EXEMPTIONS`，各带文档归属说明。
- 13 个 file-browser Remote DTO → `LINK_MAP` 的 `filesystem.md`，与 `MessageFeedbackListRequest: 'feedback.md'`、`SessionCreateRequest: 'session.md'` 等同族先例一致。

## 验证策略

- 每项改完立即单跑该 spec，不攒到最后。
- 最后跑一次全量 `npx vitest run`，与修复前的同一命令输出逐项对比。
- fixture 重写与 flake 修复各自附带**独立的无损性/有效性证明**（逻辑事件比对、竞态复现）。
- 对并发会话造成的工作树扰动，每个结论都锚定具体命令输出与独立复跑，不依赖工作树整体状态。

## 明确排除（记录归因，不修）

- `test:snapshot` 回放 69 项失败：用 HEAD 原始字节跑**未被我重写**的 `text-turn` 同样失败（`llm-replay: script exhausted`），恢复 HEAD 字节后 `fs-read` 亦失败 → 基线既有，独立问题线。
- `inspector` 5s 超时：单跑 10/10 通过，属负载敏感用例。
