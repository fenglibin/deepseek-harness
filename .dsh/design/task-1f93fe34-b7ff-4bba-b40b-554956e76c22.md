- [revision 3] ## 设计：先读后写由工具在变更前自动完成

### D1 结算位置：dsh-tool-fs/src/error.ts 的 mutateWithObservedBasis
包住「分发意图 + 提供方变更」，捕获 FS_NOT_OBSERVED 后记录观察并**重新分发意图槽位**，而非直接重试提供方调用。策略从自己的观察记录派生版本基准，因此补读后那次分发返回 `{version: vObserved}`（缺失目标返回 createIfAbsent），提供方在锁内 CAS 该版本。工具不绕开策略，只补上它缺的事实。

### D2 失败从源头不产生
`execute()` 只返回一个成功结果；中间的补读是调用内部的，不产生 `tool/result` 事件。因此会话日志里没有那行，页面也就没有那行。这是与上一轮（失败后补读）的本质区别：那一版仍产生一次 isError，只保证之后隐藏。

### D3 缺失目标交给策略作答
恢复读取发现目标不存在时发出 `{kind:'absent'}`（权威的负向观察），于是策略给出 FS_NOT_FOUND（edit 无内容可改）或 createIfAbsent（write 可创建），而不是让模型去读不存在的文件。工具不自己编造结论。

### D4 str_replace_editor 用更自然的形式
str_replace 与 insert 本就必须读取内容定位字面量/插入边界，改为**先读取并发出观察、再分发意图**。审计发现 insert 分支过去完全不做读取。

### D5 系统提示词同步
edit/write 指导段原写 "Read the file first (the default fs-observation-policy requires it)"，规则变了即成为错误指令（继续驱使模型做已无必要的 read）。改为说明工具自行结算观察，保留「edit 需要内容才能写出匹配的 old_string」这条仍成立的忠告。

### D6 策略规则本身不变
插件语义一字未改：未见目标仍被门禁拒绝，陈旧观察仍以 FS_STALE_VERSION 失败。改变的是「谁来满足它」。移除策略插件仍得到无条件变更。

### D7 语义放宽（需留意）
补读读到当前内容并记下当前版本，因此「调用之前的外部改动」不再判为陈旧，保护收窄为「读取与写入之间」的并发改动，由提供方锁内 CAS 兜住。

### 验证纪律
所有 vitest 断言走源码面（tsconfig paths → src）。产物面必须单独验证：dsh 经包 exports 解析到 lib/index.js。已用纯 node 从 lib 实际加载验证未读 edit/write 均 isError=false。
- [revision 13] ### D8 更正：运行面判定（推翻本记录早先的 D1 附注与产物面结论）

早先在本任务的设计与变更记录中曾判定"GUI 经包 exports 解析到 lib/index.js，只改 src 不生效，需重建 lib"。**该判定错误，据以行动会误导。**

实测结论：GUI 由 run.sh → `pnpm dsh` → `node --import tsx/esm apps/cli/src/bin.ts` 启动；tsx 读取 tsconfig.base.json 的 compilerOptions.paths，把 `@deepseek-ai/dsh-tool-fs` 解析到 `packages/fs/tool-fs/src`，`@deepseek-ai/dsh-tool-str-replace-editor` 同理。已在同一启动路径下用 import.meta.resolve 实测确认返回 `packages/fs/tool-fs/src/index.ts`。

因此：
- 改动无需重建 lib/ 即可被运行中的服务加载；本次执行的 `pnpm run build:lib:host` 无害但非必需。
- 仍然成立的一点：tsx 只在进程启动时加载模块，run.sh 不含 watch/HMR，因此**已运行的进程必须重启**才能载入新代码。这是用户当时仍未看到效果的唯一原因。

### D9 更正：用户问题的错误码归属

曾向用户提出一个以其所见错误文字为选项的问题，用户表示无法回答——该问题设计不当，并把诊断带偏为"FS_EDIT_NOT_FOUND，本轮修错了问题"。

更正后的诊断依据（不需用户回答即成立）：
- 用户自己的会话日志 ~/.dsh/sessions/<cwd>/<session>/session.jsonl.zstd 中，工具错误码里 FS_NOT_OBSERVED 出现最多，样例为 'Error: edit requires reading "<path>" first'。
- 用户描述"红字出现后又消失"是错误码指纹：只有 RecoveredMutationProjector 做条件式隐藏（要求同一文件后续变更成功），其集合恰为 FS_NOT_OBSERVED / FS_STALE_VERSION；FS_EDIT_NOT_FOUND / FS_AMBIGUOUS_EDIT 由 HiddenToolFailureProjector 无条件隐藏，从不"消失"。
- 用户同时询问"写入之前先读取文件这个规则可以修改吗"，正指向 FS_NOT_OBSERVED。

结论：本轮"变更前结算观察"的修复方向正确，无需回退。
