## 轮次用时面板新增「输出峰值速度（TPS）」

**时间**：2026-09-11 11:40
**类型**：新功能
**语言/技术栈**：TypeScript / React / Vitest / Playwright

### 变更内容

- `deriveTurnMetrics` 新增 `peakTokensPerSecond`：对该 turn 内每个同时具备 decode 墙钟与 provider 上报输出 token 的步骤，算 `outputTokens ÷ (decodeMs / 1000)` 并取最大值。
- 该值经 `TurnTailChatData` 与 `TurnTimePanelProps` 透传到轮次用时弹窗，渲染为「输出峰值速度（TPS）」一行，排在输出速度之后、首 token 用时之前。
- decode 墙钟为 0 的步骤不产生比值，被排除；所有步骤 decode 墙钟均为 0 时不输出该行。
- 需求中的另外两项（首 Tok 耗时、每秒平均 Tok）在改动前已由同一弹窗的 TTFT 行与「输出速度（TPS）」行提供，本次未重复实现。

## 每轮对话都披露用时与 Tok（修复分页切出的回合边界）

**时间**：2026-09-11 13:45
**类型**：修复
**语言/技术栈**：TypeScript / Cordis projection / React / Vitest

### 变更内容

- 用户反馈：同一会话里只有最后一段输出后面有用时与 Tok 信息，要求每一轮都显示，与"本轮用量"一致。
- 根因：用量 pill 读 host 侧全量折叠的 `turnUsage` 单元，每一轮都有；用时 pill 的 `runMs` 取自客户端已加载窗口的 `TurnLocation.start`/`end`，首 token 与吞吐取自窗口内 assistant 节点。历史按页加载，被切出的回合边界让 `runMs` 无从计算，于是只有边界完整的轮次显示用时。
- 新增 `turnTiming` 投影单元（`@deepseek-ai/dsh-session-stats`）：按回合号提供 `runMs`、`ttftMs`、`tokensPerSecond`、`peakTokensPerSecond`，缓冲轮内事件并在 `turn/end` 折叠，与分页无关。
- `TurnTailNodeView` 优先读该单元，窗口折叠保留为无单元装配的回退，选择顺序与用量 pill 逐字对齐。
- 两个 timing 折叠共用的首 token 判定抽到 `src/chunk-delta.ts`，消除包内第二份实现。
- 测试 harness 的 `useProjection` 原先忽略 key、恒返回 outline 形状；改为按 key 分派并新增 `turnTiming` 通道。

### 漏拦复盘

- **本次 DoD 门禁是否发现并当场修复了任何偷懒/漏实现？** 是。首版回归测试直接断言 `用时 1分2秒`，实际渲染是零填充的 `1分02秒`；且首版未提供 `turnEnds`，而 turn-tail 节点本身需要 `turn/end` 才渲染，导致断言先拿到 null。两处都当场修正。
- **上一批的漏拦（本次根因）**：上一批 Agent Note 在 Alternatives 里否决了"新增 host 侧 per-turn 时序投影"，理由是"三个指标口径一致，收益不抵成本"。该分析只推演到"分页只影响窗口边界处的那一个 turn"，与用户实际看到的"只有最后一轮有"不符；当时没有继续追问这个矛盾，而是按成本收益否决了方案。**教训：当推演结论与用户描述的现象不一致时，应继续深挖而不是按成本否决；"口径一致"本身不构成保留一个会缺数据的口径的理由。**
- **阶段 5 需求完整性校验是否发现任务级 DoD 漏拦的需求点？** 是。上一批只验证了"窗口完整时每轮都有用时"，没有覆盖"分页窗口"这一真实使用形态，DoD 缺少"数据来源是否受分页影响"这一维度。改进：凡 pill/行级展示新增或修改，DoD 追加一项"该数据在客户端分页窗口下是否完整，是否与同排其他数据同口径"。
- **本次交付是否有任何"口头说完成但实际是占位"的情况？** 否。

#### 双向修复 3 问

1. **这个 bug 是哪种通用模式？** 新增「模式 M.8：并排展示的两项数据分属不同口径（一项全量、一项窗口），对分页的敏感度不一致」。既有的 M.7（UI 行数变化击穿计数断言）覆盖的是断言失效，不覆盖这种"同屏数据不同源"的缺陷。
2. **其他语言 / 模块是否同样脆弱？已扫了吗？** 已扫：全仓库 grep `useProjection(` 的全部调用点，逐一确认数据来源。`turnOutline`（抽屉）、`tokenUsage`/`sessionStats`（统计条）都走全量单元；`turnTiming` 本次补齐；窗口折叠仅作为无单元时的回退保留。未发现其他"同排不同源"的组合。
3. **有没有写自检脚本 + 单测机器拦截这种模式？** 已落地两条单测：`turn-timing.spec.ts` 的"多轮独立"用例锁定 host 侧每轮产出；`chat-view.client.spec.tsx` 的新用例锁定"缺 `turn/start` 时仍由全量数据披露"。测试 harness 的 `useProjection` 也改为按 key 分派，避免其他 projection 的测试继续拿到错误形状的数据。

### 注意事项

- `turnTiming` 单元会为每个进行中的轮次保留轮内事件直到 `turn/end`，与 `turnUsage` 单元的成本形态相同。
- 单步回合的峰值恒等于平均，这是峰值口径本身的语义，与数据来源无关。
- 客户端窗口折叠保留为回退路径，不挂载该单元的组合行为不变。
- `chat-view.client.spec.tsx` 的 harness 原先忽略 `useProjection` 的 key，恒返回 `turnOutline` 形状；该缺陷已修复，但其余 projection 的测试仍走回退路径，如需覆盖请显式注入。
